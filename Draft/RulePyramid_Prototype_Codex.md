## 1. 游戏要验证什么

### 1.1 一句话定义

**玩家通过移动刻有文字的石块，改写建筑材料的行为，在残缺金字塔上搭建通往顶端的路线。文字石既是句子的一部分，也是可以踩踏的建筑材料。**

借鉴方向是“移动方块创造攀登路线”和“移动文字改变规则”，不要求复刻任何原作的完整规则、视觉、角色或关卡。

### 1.2 核心体验

玩家需要同时思考两件事：

- 这块石头放在哪里，建筑结构才允许我继续攀登？
- 这个词放在哪里，其他建筑石块才具有我需要的性质？

最重要的设计命题是：**同一块文字石，保留在句子里和取出来搭台阶，不能同时满足。**

暂不加入倒计时、步数限制、追赶敌人或持续坍塌压力。撤销降低尝试成本，但不等于规则上消除了死锁。

### 1.3 原型成功标准

最低完整切片必须包含：进入关卡、移动、推拉、攀爬、至少一次可观察的规则变化、建筑状态变化、登顶胜利、撤销与重开，以及在编辑器修改关卡后再次试玩。

此外，应有一关尝试验证“文字石兼作台阶”的结合点。若实际只能做出“移动文字开门”，应如实记录设计尚未融合，不要通过 UI 文案宣称核心体验已经成立。

## 3. 程序框架选择

### 3.1 总体选择

采用：**纯 C# 确定性模拟核心 + 轻量应用会话 + Unity 表现适配层 + 数据驱动编辑器。**

可以理解为轻量的 Model–Presenter–View 分离，但不引入完整 MVVM、响应式框架或依赖注入容器。最关键的边界不是模式名称，而是：**规则与空间状态不依赖 GameObject，编辑器与游戏共用同一个核心。**

| 项目 | 默认选择 | 原因与边界 |
|---|---|---|
| 引擎 | 保留项目的 Unity 2022 版本；新建默认 2022.3 | 不使用只有 Unity 6 才有的 API；不硬编码未经环境确认的补丁号 |
| 渲染 | 已有管线原样保留；全新空项目默认 Built-in 3D | 原型不需要管线迁移；已有 URP 项目沿用兼容包版本，不主动升级。2022.3 官方 URP 入口对应 14.x 文档 [U1] |
| 逻辑 | 普通 C# 类、结构体、枚举和集合 | Core 不引用 `UnityEngine` 或 `UnityEditor` |
| 模块隔离 | `.asmdef` | 用编译依赖防止逻辑层反向引用表现层 [U2] |
| 组装方式 | `GameBootstrap` 手动创建并传递依赖 | 不引入 Zenject/VContainer，不使用全局 Service Locator |
| 时序 | 离散命令驱动，一次命令完成一次结算 | 不靠 `FixedUpdate`、刚体、碰撞回调或动画事件决定结果 |
| 存档格式 | JSON 关卡文件 + 明确 DTO | 文件中不保存 Prefab、Transform 或 Unity 对象引用 |
| JSON 实现 | Runtime 中的 `JsonUtility` 适配器 | DTO 使用可序列化普通字段与列表；不要直接序列化字典 [U3] |
| 静态表现配置 | 少量 ScriptableObject | 只保存预制体/材质映射、镜头参数、关卡 TextAsset 清单，不保存游玩中的可变世界 |
| 游戏 HUD | 首版 IMGUI | 不为按钮和规则列表建立 UI 框架；以后可换 UGUI/UI Toolkit，不影响 Core |
| 三维文字 | 首版内置 TextMesh，显示英文词 | 不强制导入字体资源或额外文字包；已有项目有成熟文字方案时可沿用 |
| 作者工具 | `EditorWindow + IMGUI` | 首版用一个窗口完成分层绘制；工具类及 OnGUI 入口有官方支持 [U4] |
| 编辑器三维预览 | `PreviewRenderUtility` 封装为 PreviewHost | 隔离预览对象，不把临时内容写进用户场景；参考 Unity 官方 C# 源码 [U5] |
| 自动测试 | Unity Test Framework，核心以 EditMode 测试为主 | Unity Test Framework 支持 EditMode / PlayMode；沿用项目锁定版本 [U6] |

输入后端先检查项目：已启用旧 Input Manager 或 Both 时，可以使用旧输入适配器；仅启用新 Input System 时，使用项目已安装的新输入包。**只实现实际需要的一个后端，不修改整个项目的输入设置来掩盖适配问题。**输入适配器只输出逻辑命令。

### 3.2 明确不引入的东西

不新增 ECS/DOTS、网络框架、热更新、通用事件总线、行为树、Addressables、反射注册系统、第三方关卡编辑框架或补间库。既有工程已经使用某项时可以兼容，但不得让原型核心反向依赖它。

不为每个类建立接口。只有输入、序列化、关卡来源、表现等实际需要替换的边界才值得抽象。

## 4. 世界、坐标与物体语义

### 4.1 网格

采用 `GridCell(x, y, z)`：`Y` 向上，`X/Z` 为水平轴；水平操作仅 `±X、±Z`。Core 自行定义整数坐标值类型及相等/哈希，不用 `Vector3Int`。

关卡边界为：

```text
0 <= x < size.x
0 <= y < size.y
0 <= z < size.z
```

主动移动不能越过横向或顶部边界。`y < 0` 是下方虚空，不是隐形地面。下落到这里的建筑石被移除，角色进入失败状态。

每个实体占一格；每格最多一个实体方块。角色使用独立坐标，正常可操作状态下不能与实体方块重叠；压住失败时可以记录冲突格作为失败现场，但不允许继续操作该状态。终点是非实体标记，可以与角色同格。

角色所在格表示其身体占据的格子：若角色为 `(x, y, z)`，则 `(x, y-1, z)` 的实体方块为它提供支撑。模型的 pivot 偏移由表现层处理。

表现坐标仅由 `origin + cellSize * GridCell` 推导，Transform 不能作为反向读取逻辑坐标的数据源。

### 4.2 物体类型

| 类型 | 实体/可踩踏 | 可推拉 | 重力 | 额外约定 |
|---|---|---|---|---|
| Fixed | 是 | 否 | 无 | 锚定基础，可用于固定楼层；不模拟结构受力 |
| Red | 是 | 由 `RED IS PUSH` 决定 | 默认有 | `RED IS HOVER` 生效时免于下落 |
| Blue | 是 | 由 `BLUE IS PUSH` 决定 | 默认有 | `BLUE IS HOVER` 生效时免于下落 |
| Word | 是 | 始终可推拉 | 首版无 | 必须直接位于 Fixed 上方；只允许在这类固定台面上水平移动 |
| Explorer | 角色，不给方块提供支撑 | 玩家控制 | 有 | 无自由跳跃；无变身或多角色 |
| Goal | 否 | 不适用 | 无 | 角色在完整结算后站在该坐标且未失败，即胜利 |

所有建筑方块始终是实体。**失去 PUSH 仅意味着不能被玩家推拉，不等于固定、悬停或失去碰撞。**

### 4.3 文字石的关键限制

文字石有双重用途，但首版不允许任意搬运：可以在固定台面上水平搬动，可以被角色当作高一格的台阶；不能被举起、向上推、带离固定支撑台面，也不会因为规则变化自己下落。

这是避免“文字下落 → 新规则 → 再下落”的循环结算而做的范围控制。关卡必须把文字操作台设计成攀登结构的一部分，不能要求文字石从一楼凭空搬上二楼。

## 5. 操作协议：不要混淆推箱与攀爬

为了避免“同样撞上一块石头，有时推、有时爬”的歧义，首版把移动、推、拉定义为不同命令。

| 输入 | 逻辑命令 | 含义 |
|---|---|---|
| WASD / 方向键 | `Move(direction)` | 水平移动；遇到一格台阶时尝试攀上 |
| Shift + 方向 | `Push(direction)` | 推面前的一块，再进入该方块原来的格子 |
| Ctrl + 方向 | `Pull(direction)` | 方向指向要拉的方块；角色向反方向后退，方块进入角色原格 |
| Z | 会话 `Undo()` | 撤销整个上一次有效回合 |
| R | 会话 `Restart()` | 重置到初始关卡并清空游玩撤销历史 |

映射固定为：W/上箭头=`+Z`，S/下箭头=`-Z`，D/右箭头=`+X`，A/左箭头=`-X`。屏幕提供世界方向提示，不根据镜头旋转改写逻辑方向。

同一帧只提交一个命令。修饰键优先于普通移动；Ctrl 与 Shift 同时按下时不提交操作。编辑器中仅在试玩预览获得键盘焦点时处理游玩快捷键，不吞掉文件输入框的文字和作者撤销快捷键。

### 5.1 Move

令角色位置为 `p`，水平单位方向为 `d`，目标为 `q = p + d`。

- `q` 无实体：进入 `q`，随后由统一重力结算决定是否下落。
- `q` 有实体：仅当 `p + Up` 与 `q + Up` 都在边界内且无实体时，角色进入 `q + Up`，相当于爬上一格。
- 两种情况都不成立则拒绝；不自动转为 Push。

所有实体方块都可以成为台阶，包括可推的方块和文字石。首版角色按一格空间计算，不额外引入两格高身体碰撞体。

### 5.2 Push

`q = p + d` 必须是可推拉方块；`r = q + d` 必须在边界内且没有实体。只推一块，不连推。

验证通过后，同时把方块移到 `r`、角色移到 `q`，再重算规则与重力。红/蓝石可以被推出台面，是否悬停由当前结算中的规则决定；文字石的 `r - Up` 则必须是 Fixed。

方块上的其他方块不随它水平移动，而是保留原水平位置并参与之后的重力结算。**本版没有“推最下面一块就搬运整摞”的隐含功能。**

### 5.3 Pull

`q = p + d` 是待拉方块，角色退到 `t = p - d`，方块进入 `p`。

待拉方块必须可推拉；`t` 必须在边界内、没有实体，且 `t - Up` 有实体支撑。拉动不自动攀爬，也不允许退步时直接跨入悬空格。文字石进入 `p` 时，`p - Up` 必须是 Fixed。

按同时移动验证预留格：`p` 是角色即将让出的格子，不能因旧角色占据它就错误拒绝拉动。

### 5.4 其他运动约定

下落没有按高度计算的伤害；落到支撑上可以继续行动，落入底部虚空才失败。石块落到无法及时下落避开的角色所在格时为压住失败。具体同步顺序见第 7 节。

原型不引入朝向状态影响操作，角色视觉转身只属于表现。

## 6. 规则语法与作用范围

### 6.1 唯一支持的句法

```text
SUBJECT IS PROPERTY

SUBJECT  = RED | BLUE
PROPERTY = PUSH | HOVER
```

一条规则要求三个文字石分别位于：

```text
(x, y, z) → (x+1, y, z) → (x+2, y, z)
```

只沿世界 `+X` 读取，三个词同高度、同 Z 行，连续无空格。反向、竖直、沿 Z 轴、斜线、拐弯、跨层都不成立。文字视觉是否朝向镜头不改变解析方向。

### 6.2 规则含义

`RED IS PUSH`：本关所有 Red 允许推拉。

`RED IS HOVER`：本关所有 Red 即使下方没有支撑也保持当前高度。**HOVER 不会使石块主动上升，也不是反重力漂浮动画。**

Blue 同理。规则作用于整关，不按楼层或区域划分作用域。

多条规则使用集合并集；重复规则不叠加效果。`RED IS PUSH` 与 `RED IS HOVER` 可以同时成立。

### 6.3 规则结果是派生数据

每次有效操作后重新扫描文字布局，生成一个新的 RuleSet；不要只在旧属性上增加标记。句子被拆开时，对应属性必须立即消失。

建议运行时用枚举和属性位集合表达结果，但不要把这些结果写进关卡 JSON。每条有效句子保留三个来源方块 ID，供高亮和调试显示。

移动命令的合法性使用回合开始时的 RuleSet；完成手动位移后，新的 RuleSet 决定接下来的重力。例如拆掉 HOVER 的这个回合内，相关石块就会下落。

### 6.4 不做通用语言引擎

当前只需要三词窗口扫描和对象属性查询，不需要任意表达式 AST、解释器、脚本语言或反射执行。以后增加词汇时，可在规则定义、解析和属性解析边界内扩展，而不是在各个 BlockView 上追加特殊判断。

## 7. 确定性结算与重力

### 7.1 整步事务

一次有效输入是一整个事务：

```text
稳定状态 S0
  → 检查会话是否可接受输入
  → 根据 S0 与旧 RuleSet 规划手动操作
  → 规划失败：返回明确原因，S0 不变，不增加历史
  → 深拷贝候选状态 S1
  → 同时应用本次角色/方块手动位移
  → 重新解析文字，得到新 RuleSet
  → 按离散子步结算全部重力，直到稳定或角色失败
  → 未失败时检查终点
  → 增加回合号
  → 保存 S0 快照，提交最终状态
  → 向表现层提供结算结果与变化轨迹
```

逻辑先完成，动画随后播放。动画回调不得重新判定移动合法性或修改格子数据。

被拒绝操作不算一回合，不产生撤销记录。合法操作导致死亡仍是一回合，可以撤销。

### 7.2 重力的支撑规则

Fixed、Word、具有 HOVER 的建筑石在重力结算中不移动。其余红/蓝石仅看垂直下方一格是否能够稳定支撑；不使用边角连接、悬臂受力或物理接触面积。

任意停留的实体方块都可以提供支撑。角色不为石块提供支撑。

### 7.3 每个重力子步采用“先决定、后统一应用”

不要直接遍历字典并逐个改坐标，否则堆叠下落可能依赖枚举顺序。

推荐算法：

1. 以当前子步开始时的快照为依据，按每个竖直列从低到高检查建筑石。
2. 对不具有 HOVER 的红/蓝石：下方没有实体，或下方实体已经被本子步标记为将下落，则将其标记为下落一格。Fixed、Word、HOVER 石不标记。
3. 根据同一份快照和上述标记决定角色是否下落：角色下方没有实体，或下方实体本子步将下落，则角色也下落一格。
4. 同时应用所有位移；下落至 `y < 0` 的红/蓝石移除。
5. 角色越过底部边界则失败；否则若角色最终格被实体方块占据，则压住失败。
6. 没有任何下落则稳定；否则继续下一个子步。发生失败即可终止本回合的后续重力计算，保留失败现场供撤销。

这意味着角色站在正在下落的石块上时，可以随支撑一起下降；但不实现水平搭乘。石块落向一个仍有稳定地面支撑的角色时，会造成压住失败。

每次下落只允许一格，避免一次直接计算落点而漏过角色碰撞。

### 7.4 终止性与防御

本版文字不受重力，重力期间不会出现新句子；HOVER 不使石块上升。因而重力阶段的坐标变化只有下降或移除。

仍应设防御性的子步上限，例如 `(动态石块数 + 1) * (size.y + 1) + 1`。超过上限视为模拟错误：不提交候选状态，不消耗撤销历史，输出包含关卡 ID、回合号与命令的诊断，不把它当作玩家失败。

### 7.5 初始状态

加载顺序必须是：结构校验 → 构造临时世界 → 解析初始规则 → 检查稳定性。

不能在识别初始 HOVER 之前先让悬空石块掉下去。本版要求关卡初始状态已经稳定；若试结算会移动物体或杀死角色，拒绝开始试玩并指出问题，不静默改写作者的初始布局。

## 8. 撤销、重开与会话边界

### 8.1 使用完整逻辑快照

首版选择快照而不是逆向命令。一次操作可能同时拆掉规则、移动多块石头、移除掉入虚空的石块并改变输赢状态，仅反向移动最初那块石头是不正确的。

快照至少包含角色位置、全部存活方块及稳定 ID、方块类型与文字、回合号、运行/胜利/失败状态及失败原因。关卡静态定义可以共享只读引用，但所有会变化的列表、字典和对象必须深拷贝或真正不可变。

恢复时重建占用索引并重算 RuleSet，不能沿用另一个时刻的属性缓存。被移除方块必须能恢复，实体 ID 不得变化。

### 8.2 两类历史互不混用

- 游玩 Undo：恢复上一个有效回合前的完整 WorldState。
- 编辑 Undo/Redo：恢复作者的关卡草稿，不受推拉、PUSH 或重力约束。

游戏首版不要求 Redo；编辑器要求 Undo/Redo。两个历史栈不得共享。

### 8.3 交互细节

动画播放中不接受新移动，但允许 Undo/Restart 打断；表现层先取消旧动画，再重建或立即同步到恢复后的状态，避免旧协程回调把画面又移回去。

可用递增的表现世代号取消过期动画回调，或集中管理并明确停止所有相关动画。

胜利不自动切关，先显示胜利界面，保留撤销按钮。失败不自动重开，同样保留撤销。

Restart 恢复最初的稳定快照并清空游玩历史；首版不支持撤销 Restart。不设置人为步数上限，但历史仍消耗真实内存；不要把“支持连续撤销”宣传成逻辑无死锁。

## 9. 核心类型与职责

下面是职责契约，不要求每项都是接口或单独文件。

| 类型 | 责任 | 不能做什么 |
|---|---|---|
| `GridCell / GridBounds` | 整数坐标、方向与边界 | 不引用 Vector3/Transform |
| `LevelDefinition` | 可保存的初始关卡文档 | 不保存活动规则和 GameObject |
| `BlockDefinition / CellData` | JSON 可序列化数据 | 不含 Unity 引用或字典 |
| `WorldState` | 当前角色、方块、状态、占用索引 | 不由 View 直接修改 |
| `WorldFactory` | 从校验后的关卡创建稳定会话初态 | 不静默修复错误关卡 |
| `RuleParser` | 文字坐标转规则集合与来源 | 不移动物体 |
| `PropertyResolver` | 根据物体类型与 RuleSet 查询 PUSH/HOVER | 不维护第二份可变属性真相 |
| `MovePlanner` | 在旧状态上验证并规划手动位移 | 不在验证过程中修改原状态 |
| `GravityResolver` | 按新规则计算确定性下落 | 不调用 Physics |
| `SimulationEngine` | 组织一次完整回合 | 不依赖输入设备、动画或文件 |
| `GameSession` | 当前状态、初始状态、游玩历史、终局限制 | 不混入 EditorWindow 逻辑 |
| `LevelValidator` | 结构与初始稳定性诊断 | 不声称基础校验证明可解 |
| `LevelEditSession` | 草稿、编辑命令、作者撤销/重做、脏标记 | 不复用玩家 Push 作为绘图操作 |
| `UnityLevelSerializer` | JSON 与 LevelDefinition 转换 | 不在 JSON 中保存引用或运行快照 |
| `GamePresenter` | 把会话结果转换为 View 更新 | 不决定输赢、重力、支撑 |
| `WorldView / BlockView` | 生成模型、文字、位移、高亮 | 不通过碰撞回调写逻辑 |
| `LevelEditorWindow` | 窗口布局、鼠标键盘、调用编辑会话 | 不维护独立的规则实现 |

模拟的主要入口可采用如下形式，最终签名允许按现有代码风格调整，但含义必须保持：

```text
WorldFactory.TryCreateStable(level) → CreateWorldResult
RuleParser.Parse(world) → RuleSet
SimulationEngine.TryStep(sourceState, command) → StepResult
GameSession.TryExecute(command) → StepResult
GameSession.Undo() / Restart()
LevelValidator.ValidateStructure(level) → ValidationReport
LevelValidator.ValidateForPlay(level) → ValidationReport
LevelEditSession.Apply(editCommand) / Undo() / Redo()
```

`StepResult` 必须区分接受/拒绝/模拟错误，包含最终状态、拒绝或失败原因，以及用于动画/调试的阶段变化。被拒绝的 Step 不得修改传入的 sourceState。

首版调试轨迹可只用普通列表记录“手动移动、规则增删、每个下落子步、移除、终局”，不需要事件溯源框架。

## 10. 关卡文件：从第一天就为编辑器准备

### 10.1 单一数据源

**关卡 JSON 是布局的唯一持久化数据源。**Unity Scene 只存启动器、镜头和表现依赖，不以一堆手摆方块作为另一份权威关卡数据。

游戏加载、编辑器打开、编辑器试玩和解法回放都经过同一套 LevelDefinition、序列化适配和校验入口。

区分三个对象：

```text
磁盘上的 LevelDefinition
        ↓ 深拷贝
作者正在修改的 LevelEditSession.Draft
        ↓ 深拷贝并校验
试玩中的 GameSession.WorldState
```

三者不能共享可变列表。停止试玩后返回原草稿，而不是将试玩残局保存成关卡。

### 10.2 v1 数据字段

| 字段 | 类型 | 约定 |
|---|---|---|
| `schemaVersion` | int | 当前必须为 1；未知版本拒绝加载 |
| `ruleSetId` | string | 当前必须为 `rule-pyramid-v1`；防止规则含义变化后静默误读 |
| `levelId` | string | 稳定标识；建议小写字母、数字、下划线或短横线 |
| `displayName` | string | 显示名称，可中文 |
| `size` | CellData | 各轴格子数，必须为正数 |
| `playerSpawn` | CellData | 角色身体所在格，而非脚下石块的坐标 |
| `goal` | CellData | 终点角色格；不是终点支撑石的坐标 |
| `blocks` | BlockDefinition 列表 | 所有固定基础、建筑石和文字石 |
| `blocks[].id` | int | 本关唯一正整数，保存和移动后保持不变 |
| `blocks[].kind` | string | 严格为 `Fixed / Red / Blue / Word` |
| `blocks[].token` | string | Word 为 `RED / BLUE / IS / PUSH / HOVER`；其他类型为空字符串 |
| `blocks[].position` | CellData | `{ "x": int, "y": int, "z": int }` |

DTO 使用普通可序列化类及 public 字段。`CellData` 等嵌套 DTO 建议使用可空引用类，便于识别整个必填子对象缺失；进入 Core 的运算状态时转为 `GridCell` 值类型。

不要依赖反序列化调用构造函数来补必填数据。缺失版本、类型、位置对象或列表必须报错；坐标分量在 v1 中按普通整数默认值处理，编辑器保存时始终显式写出 x/y/z。需要更严格的字段存在性检查时，应在序列化边界加强，不把脆弱的字符串搜索散落到游戏逻辑中。

JsonUtility 使用字段序列化，不支持直接保存 Dictionary；根对象也应是包装类，而不是直接传入数组 [U3]。运行时为查询性能建立的字典不进入文件。

### 10.4 保存、读取与版本边界

保存前结构校验；序列化时按稳定顺序输出 blocks，例如 `(y, z, x, id)`，避免同一布局每次产生无意义 Git diff。移动方块不重分配 ID；复制方块分配新 ID。

正常保存和发布关卡要求结构合法；作者尚未完成的草稿可以留在编辑会话和临时备份中，不静默清理或删除错误元素。

写入文件必须捕获 IO/权限异常。先写同目录临时文件，再以适合目标环境的替换方式提交；失败时尽量保留原文件和可恢复草稿。不要宣称所有文件系统上的替换都天然原子。

已有文件覆盖由明确的 Save/确认覆盖操作触发，不在试玩结束或切层时自动覆盖。

首版关卡放在 `Assets/_RulePyramid/Content/Levels/`，通过一个 `LevelCatalog` 的 `TextAsset` 引用列表进入构建。运行时读取 `TextAsset.text`，不能依靠 `AssetDatabase` 或直接读 `Assets/...` 路径来加载发布版关卡。

外部 JSON 导入与运行时编辑器属于后续方向：在关卡来源接口上预留即可，不必本轮实现完整文件浏览器、云端仓库和关卡市场。

未知 `schemaVersion` / `ruleSetId` / kind / token 返回可读错误，不做静默猜测。未来真的出现 v2 时再实现明确迁移函数；不要现在创建空的通用迁移框架。

## 11. 关卡编辑器设计

### 11.1 首版定位

入口：`Tools/RulePyramid/Level Editor`。

首版是给开发者制作关卡的 Unity 工具。**关卡文档与编辑逻辑放在 Core，窗口、预览渲染、资产导入放在 Editor。**以后做打包后的玩家编辑器，只替换 UI、文件来源和预览宿主，不另写物体定义与规则模拟。

### 11.2 窗口布局

```text
┌──────────────────────────────────────────────────────────────────┐
│ New  Open  Save  Save As  Undo  Redo  Validate  Playtest / Stop     │
├──────────────────────────────────┬───────────────────────────────┤
│ 关卡 ID / 名称 / 尺寸             │ 三维预览                      │
│ 当前 Y 层： [ - ]  1  [ + ]       │ 固定斜视；编辑时可旋转观察     │
│                                  │                               │
│ XZ 二维格子画布                   │ 实体、文字、出生点、终点      │
│                                  │ 当前层标识、选中方块高亮      │
├──────────────────────────────────┼───────────────────────────────┤
│ 画笔与选中对象属性                │ 当前生效规则 / 校验问题       │
│ Fixed / Red / Blue / Word         │ 点击问题定位到对应层和格子    │
│ Spawn / Goal / Erase              │                               │
└──────────────────────────────────┴───────────────────────────────┘
```

二维视图：X 向右，Z 向上；始终显示坐标和当前高度。切层改变的只是作者视图，不改变关卡数据。

### 11.3 必须支持的作者操作

| 操作 | 行为 |
|---|---|
| New | 创建空草稿；要求设置名称/尺寸，并保留未保存提示 |
| Open | 读取 JSON，经解析和校验后替换草稿；有脏数据时先处理保存/放弃/取消 |
| 分层画笔 | 在当前 Y 层放置或擦除 Fixed、Red、Blue、Word |
| Word 设置 | 从合法词汇中选择，不允许任意字符串进入模拟 |
| Spawn / Goal | 独立标记；重新放置时移动已有标记，不创建多个角色或多个终点 |
| 选择/属性 | 查看 ID、类型、词、坐标；可修改位置或词汇 |
| Undo / Redo | 针对作者操作；一笔连续涂绘作为一个历史步骤 |
| Resize | 越界物体存在时拒绝缩小并指出对象；不得悄悄裁掉 |
| Save / Save As | 保存完整文档；失败不丢失草稿 |
| Validate | 显示错误与警告，允许跳转坐标 |
| Playtest / Stop | 在隔离的会话中试玩，结束后恢复原草稿 |

同一格已有实体时，画笔替换行为应清晰可见且可撤销。实体层与 Spawn/Goal 标记层分开：擦除实体不得无声删除终点，放置实体到标记格应显式提示或让校验显示冲突。

作者绘图不受游戏规则限制。例如暂时没有 `RED IS PUSH`，仍可以在编辑器移动红石。允许处于未完成的中间草稿状态，但不能把无效草稿当作可试玩关卡。

### 11.4 编辑模型必须独立于 UnityEditor

`LevelEditSession` 持有 Draft、编辑历史、当前修订号和脏状态。编辑命令可用简单枚举加参数或几个小类实现，例如：

```text
PlaceBlock / RemoveBlock / MoveBlock / SetWordToken
SetSpawn / SetGoal / ResizeBounds / SetMetadata
BeginStroke / EndStroke
```

无需提前实现任意可扩展命令总线。小地图可以在每笔操作前保存整个草稿快照，优先正确性。

保存后的“是否有未保存修改”要根据内容或保存修订点判断。撤销回已保存内容时可以清除脏标记；不要仅用“发生过任何操作”的永久布尔值。

### 11.5 三维预览

预览复用 Runtime 的模型/材质/文字生成逻辑，但不接管或污染作者当前场景。使用独立 PreviewHost 管理 `PreviewRenderUtility`、临时对象和相机；窗口关闭、脚本重载或重新创建预览时正确清理资源 [U5]。

编辑预览需要展示尚未合法的草稿，因此不能强制通过 WorldFactory 才显示内容。可以从 LevelDefinition 直接构建只读布局预览；真正开始试玩时才必须完整校验。

预览相机旋转只改变观察方式，不改变坐标、句法方向或操作语义。提示规则沿世界 `+X` 读取。

已有 URP 工程中，应验证预览使用的材质和渲染调用与当前管线匹配。出现预览黑屏时修复 PreviewHost，不通过切换整个工程的渲染管线规避问题。

### 11.6 试玩隔离：首版不必自动切换 Unity Play Mode

推荐在编辑器窗口内创建独立 GameSession 试玩，流程为：

```text
编辑草稿
  → ValidateForPlay
  → 深拷贝并创建新的 GameSession
  → 禁用作者绘制，切换到试玩输入与状态显示
  → 使用相同 SimulationEngine、规则解析和撤销逻辑
  → Stop
  → 丢弃试玩会话，重新显示未被修改的作者草稿
```

这样无需依赖 Unity 切换 Play Mode 的静态变量传参，也不需要把临时关卡写进用户场景。试玩中的 Undo 操作的是 GameSession，不是作者历史。

**窗口内试玩不是完整 Unity Play Mode 验收的替代品。**还必须运行 `Prototype.unity`，检查实际输入、HUD、场景加载和构建依赖；可用环境具备构建模块时再做独立运行验证。

### 11.7 脚本重载与数据保护

草稿发生修改时，可将草稿 JSON、当前层和源路径保存到项目隔离的 `SessionState` 临时键中。SessionState 能跨程序集重载保存编辑器会话信息，但 Unity 退出后会被清除，因此它不是正式存盘 [U7]。

重载后允许恢复草稿；试玩会话可停止并返回草稿，不要求恢复正在播放的动画。作者 Undo 历史首版可不跨重载，但必须保住当前草稿并说明历史已重置。

关闭脏文档时提供 Save / Discard / Cancel。不要在窗口 OnDisable 中无条件把临时状态覆盖到原关卡文件。

### 11.8 校验分级

| 分类 | 示例 | 处理 |
|---|---|---|
| 结构错误 | 未知版本、尺寸无效、重复 ID、重复实体格、未知类型/词、元素越界、缺少出生点/终点 | 阻止正式保存与试玩 |
| 游玩前错误 | 出生点被实体占据、出生点无支撑、初始场景不稳定、文字石不是直接位于 Fixed 上方、终点初始被实体占据 | 允许结构合法的草稿保存；阻止开始试玩 |
| 设计警告 | 没有有效规则、没有建筑石、终点不高于出生点、地图较大、可能存在不使用规则的登顶路线 | 展示提示；不伪装成严格证明 |

终点下方暂时没有支撑可以是谜题的一部分，不应直接判为错误。终点在首版要求初始格空闲，但可以等待玩家之后搭好支撑。

基础校验不证明关卡可解或不存在绕解。不要把普通二维 Sokoban 的角落死锁规则直接用来禁止本游戏操作；这里存在高度、攀爬、拉动与属性切换。

## 12. 表现与调试要求

### 12.1 画面最低要求

镜头固定斜视、优先正交，能看到主要操作面与终点。关卡是带缺口和高度障碍的局部阶梯，不是可以从外围直接走上去的完整金字塔。

Red 与 Blue 除颜色外再显示 `R/B` 标记，减少仅靠颜色辨认的负担。Word 上显示英文词，生效句子的三个词有明显描边、底色或连线；使用同一份 RuleSet 来源 ID 做高亮。

文字可朝向镜头展示以保证阅读，但不得让视觉朝向影响逻辑。当前规则列表提供稳定可见的信息来源。

### 12.2 HUD

至少显示当前关卡名称、操作说明、当前有效规则、撤销/重开、最近一次拒绝原因、胜利/失败状态。步数可以用于调试显示，不是通关限制。

开发调试区域可展开显示角色坐标、选中方块 ID、当前回合号和本次结算轨迹。失败原因应区分“落入虚空”和“被石块压住”。

### 12.3 动画与逻辑分离

首版允许瞬移表现；插值是 P1 或在不影响 P0 的情况下增加。无论有没有插值，模拟结果必须完全一致。

增加动画时，优先按“手动位移 → 规则变化 → 下落子步”播放，避免玩家看不出因果。最终表现位置必须重新对齐格子中心，不累计浮点偏移。

不把动画完成作为逻辑回合完成条件。GameSession 已提交状态，Presenter 只是暂时屏蔽新的移动输入；Undo/Restart 可以取消当前动画。

## 13. 关卡内容的制作顺序

### 13.1 第一份：操作冒烟测试

直接使用第 10 节示例，检查加载、推石、攀上一格、抵达终点与撤销。它允许其他路线，不作为设计质量证明。

### 13.2 第二份：集成关卡，优先于“多做几关”

设计目标是以下因果链中的至少一条完整成立：

```text
拼出 HOVER → 利用悬停石搭路 → 到达新操作位 → 改写规则 → 登顶
```

更有价值的目标是：

```text
保留一句规则建立临时路线
  → 利用路线补上实体支撑或完成空间安排
  → 规则不再必需
  → 回收句子中的文字石作为最后一级台阶
```

这是关卡命题，不是现成且已证明可解的地图。Codex 必须依据本版运动规则搭实际坐标布局、记录可执行操作序列并测试，不能仅把文字描述当作完成。

制作时特别检查：

- HOVER 不会抬高石块；必要的高处石块应初始就在那个高度，或能够在同一高度被推出去。
- Word 只能在 Fixed 台面上水平移动；不能要求把词举上楼，或把词推到普通建筑石上。
- 普通 Move 可以爬上任何单格实体，不需要先给它 PUSH。避免本来想要求改规则，实际却能直接踩上去绕过。
- 允许拉动会扩大可达空间；不要照搬只有推的关卡而不检查逆向操作。
- 金字塔外沿不能天然成为不需要操作的连续楼梯。

至少记录一条从初态到胜利的合法解法；这证明“有解”，不证明“唯一解”或“必须使用所有机制”。针对明显替代路径另做人工检查，未做穷举不要宣称无绕解。

### 13.3 第三份：P1 教学拆分

若集成关卡验证成立，再拆出短教学：一关只讲 PUSH，一关只讲 HOVER，最后一关讲文字与台阶共用。不为凑关卡数量增加新规则。

## 14. 自动测试与验收用例

### 14.1 必须覆盖的测试类别

Unity Test Framework 的 EditMode / PlayMode 能力依据见 [U6]。大部分逻辑用不加载场景的 EditMode 测试验证；场景与表现再做 PlayMode 或人工验收。

| 编号 | 用例 | 预期 |
|---|---|---|
| T01 | 空格移动、单格攀爬、顶部/横向边界、攀爬头顶被挡 | 合法位置正确；非法操作不修改状态 |
| T02 | Move 面对可推石 | 尝试攀爬，不自动推 |
| T03 | Red 无 PUSH / 有 PUSH 时使用 Push | 前者拒绝，后者按规则执行 |
| T04 | Word 没有任何有效句子时被推拉 | 仍可操作，但必须满足 Fixed 支撑限制 |
| T05 | Word 推向无支撑格或 Red 上方 | 拒绝；不能破坏文字台面不变量 |
| T06 | 前面连续两块石时 Push | 不支持连推，不发生半完成移动 |
| T07 | Pull 把石头拉进角色旧位置 | 允许让出的格子被占用；角色正确后退 |
| T08 | Pull 后退格悬空或被占用 | 拒绝，不自动攀爬或下落拉动 |
| T09 | 正向连续三词 / 反向 / 跨层 / 沿 Z / 缺词 | 仅满足 +X 三词协议时生效 |
| T10 | 移动词拆掉 HOVER | 当回合移除属性，相关石块开始下落 |
| T11 | 同一主体 PUSH 与 HOVER 并存、重复句子 | 属性并集正确，重复句子不重复执行效果 |
| T12 | 悬空石块有 HOVER | 保持高度，不主动上升 |
| T13 | 悬空多层石堆失去 HOVER | 按同步子步落下，结果不依赖字典插入顺序 |
| T14 | 角色站在将下落的石头上 | 按同一子步一起下降，落地后不穿模 |
| T15 | 石头落向有稳定支撑的角色 | 标记压住失败，可撤销 |
| T16 | 石头/角色从 y=0 再下落 | 石头移除 / 角色落入虚空失败 |
| T17 | 操作合法但导致失败 | 提交失败状态，增加一条可撤销历史 |
| T18 | 被拒绝操作 | 原状态、回合号、历史长度都不变 |
| T19 | 撤销包含规则变化、下落、石头移除的回合 | 所有坐标、ID、规则和状态恢复 |
| T20 | 失败后撤销、胜利后撤销、重开 | 正确恢复；重开清空历史 |
| T21 | 初态已有 HOVER 的悬空石 / 无 HOVER 的悬空石 | 前者稳定可加载，后者给出初始不稳定错误 |
| T22 | JSON 保存后读取 | ID、位置、词、尺寸、出生点和终点保持一致 |
| T23 | 重复 ID/格子、未知版本/词、损坏 JSON | 清晰报错，不替换当前有效文档或会话 |
| T24 | 编辑器试玩后 Stop | 草稿内容和保存文件完全未被试玩修改 |
| T25 | 编辑 Undo/Redo 与游玩 Undo | 历史独立；撤销回保存状态时脏标记正确 |
| T26 | 同一关卡重播同一组命令；打乱块列表插入顺序再播 | 规范化状态与终局一致 |
| T27 | 正式运行程序集检查 | 不引用 UnityEditor，构建加载不依赖 Assets 文件路径 |

可以合并为参数化测试，不要求一编号一个文件。每修复一个结算 bug，补一个最小回归布局与命令序列。

### 14.2 冒烟关卡的明确命令序列

使用第 10 节 JSON，初始应存在 `RED IS PUSH`，角色为 `(0,1,0)`。

| 步骤 | 命令 | 角色结果 | 红石 ID=12 | 状态 |
|---|---|---|---|---|
| 初始 | — | `(0,1,0)` | `(2,1,0)` | Running |
| 1 | `Move(+X)` | `(1,1,0)` | `(2,1,0)` | Running |
| 2 | `Push(+X)` | `(2,1,0)` | `(3,1,0)` | Running |
| 3 | `Move(+X)` | `(3,2,0)` | `(3,1,0)` | Running |
| 4 | `Move(+X)` | `(4,2,0)` | `(3,1,0)` | Won |
| 撤销 | `Undo()` | `(3,2,0)` | `(3,1,0)` | Running |

这份向量应转成自动测试。Unity 实际实现仍需运行验证，不以文档中的预期表格代替测试结果。

### 14.3 两个精确的局部重力测试

这些是 GravityResolver 的单元测试输入，不要求组成完整作者关卡。RuleSet 可以在测试中直接构造。

**G1：堆叠与角色同步下降。**同列 `(x,z)=(0,0)`：Fixed 在 y=0；Red 在 y=2；Blue 在 y=3；角色在 y=4；Red/Blue 均无 HOVER。结算后应分别位于 y=1、y=2、y=3，角色未失败。改变两块动态石的插入顺序应得到相同结果。

**G2：压住。**同列 Fixed 在 y=0，角色在 y=1，Red 在 y=2 且无 HOVER。角色有地面支撑不下落，Red 下落到 y=1，产生压住失败。测试只验证该失败语义，不把这样的不稳定布局当作合法初始关卡。

### 14.4 人工验收

从 Unity 菜单搭建或修复原型后，必须能进入 Prototype 场景。操作者不需要逐个手工添加脚本、创建几十块方块或补关键引用。

打开编辑器，新建小关卡，画两层固定基础和文字操作台，放置出生点/终点，保存，关闭并重新打开，然后试玩、移动、撤销、停止试玩；确认编辑草稿与文件内容没有变成试玩残局。

实际 Game View 中检查文字可读、按键方向与提示一致、规则增删可见、死亡后可撤销。支持的桌面构建环境中，确认打包后依然能加载关卡，且没有 Editor-only 依赖。

## 16. Codex 实施约束与工程交付

### 16.1 开始前检查

读取实际 Unity 版本、`Packages/manifest.json`、`packages-lock.json`、输入后端、渲染管线和现有程序集；记录到进度文件。不要擅自下载大型资源或安装第三方插件。

原型代码使用 Unity 2022 工程支持的语言/API 范围，不依赖较新 .NET 的专属 API、source generator 或复杂构建链。

没有既有项目时，生成可导入 Unity 的完整目录与明确初始化入口；实际 Editor 安装、许可证或构建模块不可用时，报告具体缺口，不伪造 `.unity` 场景 GUID 和已运行截图。

### 16.2 场景与资产初始化

提供 `Tools/RulePyramid/Create or Repair Prototype` 菜单，使用编辑器 API 创建缺失的原型场景、基础材质、必要配置与关卡清单。

该菜单应可重复执行，且只管理明确属于原型的生成资源。不得无提示覆盖用户修改过的场景、Prefab 或关卡；不得清空整个 Build Settings。需要加入原型场景时采用增量方式。

能使用 Unity 编辑器 API 创建的资产，不要手写脆弱的 YAML 与猜测 GUID。只有实际生成或验证了场景，才报告“打开即玩”；否则明确写出唯一必要的初始化菜单步骤。

### 16.3 代码纪律

不通过对象名称识别规则主体；用保存的 kind/token/ID。不要在每块石头上扫描全场景，也不要在每帧重新读取 JSON。所有规则计算由 GameSession/SimulationEngine 的固定入口触发。

避免全局可变单例保存当前世界，确保可以同时存在作者草稿、预览会话和测试会话。各种索引与属性缓存只有一份明确的重建来源。

序列化、文件 IO、界面输入、核心结算分别报告错误。禁止用空 catch 把错误吞掉，也不要在内部错误发生时假返回胜利或加载默认关卡掩盖问题。

小型原型优先清晰直接的实现。完整世界快照、整关文字扫描、按需重建预览都可接受；不提前为海量实体优化。

### 16.4 每阶段报告格式

```text
本阶段完成：
修改的主要文件：
实际执行的验证：
验证结果：
未验证项及原因：
已知限制 / 剩余 P0：
下一阶段：
```

“已编写测试”“测试通过”“Unity 编译通过”“人工试玩通过”“独立构建通过”是不同的状态，必须分开记录。未经运行的集成关卡应标记“待验证”，不能因为 JSON 结构合法就标记“可通关”。

### 16.5 最终交付清单

- [ ] Core、Runtime、Editor 和测试程序集边界正确。
- [ ] Prototype 启动入口与最小必要配置完整。
- [ ] 第 10 节 JSON 已落地，并通过对应冒烟序列测试。
- [ ] 至少一关集成关卡有记录下来的合法通关序列。
- [ ] 当前规则可见，文字石可操作并可作为台阶。
- [ ] 整回合 Undo 能恢复规则、石块移除和失败状态。
- [ ] 编辑器可以新建、打开、保存、预览、校验、试玩、返回编辑。
- [ ] 试玩不会污染草稿或文件，编辑历史和游玩历史独立。
- [ ] 测试覆盖关键运动、重力、规则变化与文件往返。
- [ ] README 说明 Unity 版本、启动方式、操作、编辑器使用、已知限制。
- [ ] IMPLEMENTATION_STATUS 区分已实现、已运行验证、尚未验证。
- [ ] 有条件时完成实际桌面构建；无条件时明确说明未构建的环境原因。

## 17. 后续扩展：现在应预留什么，不应预做什么

| 后续需求 | 现在必须保留的边界 | 现在不要做的内容 |

| 打包后的玩家编辑器 | LevelDefinition、LevelEditSession、Validator、GameSession 不依赖 UnityEditor | 一整套运行时 UI、云上传、账号系统 |
| 更多文字属性 | 规则解析与属性查询集中，关卡有 ruleSetId | 任意 DSL、插件式解释器 |
| 文字受重力 | 重力和规则阶段职责清晰、整步快照完整 | 在 v1 偷偷加入循环重解析并改变本文语义 |
| 多方向句子 | RuleParser 不与镜头绑定 | 现在实现 X/Y/Z/反向/对角线全解析 |
| 新美术和动画 | View 配置与逻辑 ID 解耦 | 用模型形状或碰撞体决定解谜结果 |
| 回放/自动求解 | 命令纯数据、模拟确定性、可取得规范化状态 | 现在写完整搜索器或套用不适用的死锁剪枝 |
| 大型金字塔/多个区域 | 关卡数据独立于场景，核心不依赖固定地图尺寸 | 流式加载、分区世界、动态寻路系统 |

核心原则：**预留替换边界，而不是提前实现所有可能性。**
