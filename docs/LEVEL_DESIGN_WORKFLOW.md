# 关卡设计工作流：逐关八工序与多关卡联合审核

生效日期：2026-09-27。适用于本项目新增关卡，以及改变教学目标、尺寸、布局、规则安排或解法的关卡重做。

玩法仍以 [当前规格](PROTOTYPE_SPEC.md) 及其最新用户修订为准；本文件规定设计与制作顺序，不改变 RW-v0.9 / schemaVersion 9。编辑操作见 [关卡编辑器指南](LEVEL_EDITOR_GUIDE.md)，逐关填写 [设计卡模板](templates/LEVEL_DESIGN_CARD.md)。

## 1. 强制工作方式

**先明确关卡目的与空间预算，再搭建可回修的地图原型 JSON。** 原型完成后审查教学反馈和解题逻辑，再验证实际解法与盲测；不得以已有 JSON 代替设计依据或验证证据。

默认按阶段交付并由用户确认后进入下一阶段。每次交付包含：当前阶段、具体方案、理由、待定项、验收依据、下一步。确认记录必须对应设计卡版本，不得自行填写“用户已确认”。既有明确确认持续有效，不重复询问；用户明确授权连续推进哪些阶段时，可在该范围内依序执行，但仍须保留各阶段产物与检查证据，不得合并成一步生成。沉默不等于确认。

- 工序 1—2：确定定位、阶段目的、空间关系和尺寸预算；工序 3 即搭建逐阶段地图原型并输出 JSON。
- 工序 4—5：依据原型审查教学反馈与解题逻辑，发现问题可回到工序 2 或 3 修改并重审受影响结论。工序 6 才能将实际回放记为解法验证；纸面推演不能标为已运行验证。
- 不以批量生成十二关、替换旧设计包、自动修复场景等方式绕过流程。批量排课可以先做，但每关都要有独立设计卡。
- 纯错别字、显示修复或参考解重录，若不改变设计意图，可沿用已确认设计，只复核受影响阶段并记录理由。布局修复仍要查尺寸、解法和教学影响。
- 发现上游错误时退回对应阶段，更新版本并使受影响的下游结论失效，不靠补提示掩盖设计问题。

当前这是作者与代理的工作约定；编辑器尚无阶段审批界面，也不会自动阻止未完成设计卡的保存。

以上确认节点适用于新增或重做具体关卡的设计，不适用于本轮阶段编辑器功能开发；编辑器可按已确认需求连续实现。阶段地图编辑不代表任何关卡已通过设计工序。

## 2. 游玩阶段与逐关设计

每关按设计安排 P1—PN 个游玩阶段（N≥1），数量由关卡内容决定。P1—PN 是玩家经历的游玩阶段，第 3 节的 1—8 是作者制作工序，两者不可混用。单关写明各阶段的目的、结构、重布、学习结果和验证依据，不须将 Teach–Test–Twist 逐项映射到每关或每个阶段。教学链在多关卡联合审核时检查，见第 6 节。

每关仍须说明玩家如何观察、尝试、得到反馈和恢复；解题验证须检查合法解及绕过本关目的的路径；盲测记录实际理解与误解。允许多解，不添加隐藏的指定操作通关条件。现有 L01—L12 不自动转换。

### 2.1 独立阶段地图与固定初态

**各阶段是独立地图，按设计延续结构，不继承玩家残局。** 例如 P1 与 P2 可分别保存为 `L1P1.json` 和 `L1P2.json`。每张地图独立记录 bounds、地形、实体、词牌、出生点和参考解，不在单张地图上涂色标记开放区域。下一小节从作者预设的完整初态开始；同一小节无论通过哪条合法解法结束，进入下一小节得到的布局都相同，不以玩家通关时箱子位置、词牌排列或变形结果作为输入。

| 内容 | 小节切换时的处理 |
|---|---|
| 固定 Terrain、地标与坐标 | 可保留可辨认的地标，也可为阶段目的局部移动、增删地形；逐项说明变化原因与空间关系 |
| 地图范围与地形变化 | 每阶段独立记录 bounds 与地形；后阶段边界不必包含旧范围，记录新增、移除区域及连接方式 |
| Object，包括箱子、旗帜、ROBOT、CLOUD、SPRING、WALL | 按下一小节配置重新生成种类、数量、身份及位置；没有通关时的位移或变形继承 |
| Text，包括隔离源词区 | 按下一小节配置重新布置，实际解析产生规则；上一小节的拆句、改词和规则状态不继承 |
| 当前 YOU 与出生点 | 由下一小节世界句子及实体位置决定；每节填写出生点与设置理由，不假定永远控制 ROBOT |
| 胜利、运动、回合与提示状态 | 建立新的小节会话；上一节的胜利锁定、弹跳顶点、自动运动和提示队列不带入 |
| 已完成小节进度 | 由关卡外层阶段管理保存，不作为物体属性或隐藏胜利条件 |

这里的“结构”指各阶段有意延续的地标与空间关系，不代表多阶段共享同一份 Terrain 数据或必须保留全部旧地形。WALL 属于受规则影响的 Object，应列入物件重布清单，不能因为外形像墙就当作固定 Terrain。地形或 WALL 变化影响通路时，要明确展示并复核教学影响。

阶段变化可以是扩图，也可以是在相近范围内局部调整地形；无需逐阶段累积扩图。保留地标有助于辨认过渡，但移动或删改平台、房间、通路时必须在差异表说明具体位置、原因及教学影响，并回修受影响的空间预算与原型。新增空间必须带来新的决策，不能只是扩大空白边界。

### 2.2 出生、目标与规则重布

- 每节分别设计出生点，优先让玩家看见新区域入口、当前目标及关键规则；换出生点不以更换受控物种为前提。若更换物种或规则，那本身也需要教学依据。
- 过渡时清楚呈现“阶段完成 → 地图变化与物件重布 → 新出生点和新目标”。可保留熟悉地标帮助辨认；局部地形变化须有可理解的呈现，具体动画和继续方式在实现时确定。
- 明确旧目标在下一节是移除、迁移、还是保留为合法目标。旧 FLAG 仍存在且 `FLAG IS WIN` 生效时，它仍然是合法目标；不能仅在后台把旧 ID 标为不可获胜。
- 每阶段的成功按当前统一合同判定：存活实例自身同时 YOU/WIN，或两个不同 YOU/WIN 实例合法同格。P1—P(N-1) 的胜利供外层阶段管理推进，PN 的胜利完成整关；N=1 时 P1 直接完成整关。不得在模拟内部加“已操作指定物体”门槛。
- 新规则作用于当前整张地图的匹配对象，不按新旧区域隔离。每次重新布词都需列出对旧区域对象的影响，检查意外成句、额外 WIN、多 YOU、失控与不支持的运动组合。
- 后续阶段的地图内容不应提前参与当前小节的碰撞、规则解析或提示触发。当前阶段只加载自身完整地图定义；不能仅把未来词牌渲染隐藏而继续让它们生效。

当前已实现：Z 只撤销当前阶段，R 恢复当前阶段预设初态；阶段切换建立新的撤销历史与提示会话，小节内撤销/重开仍遵守现有提示触发记录语义。阶段进度限当前运行会话，整关重玩独立按钮及跨启动存档另行设计。

### 2.3 可变阶段设计与验证要求

设计卡必须同时具备整关总表和 P1—PN 的独立记录：阶段目的、预期学习结果、各阶段地图文件与尺寸、地形增删移动及原因、保留地标、连接口、物件/词牌差异、出生点、旧目标处理、关键解法及证据。每张阶段地图的边界均须在每轴 1–64 格内。末阶段应有明确收束目的；若有旧区域或已学关系，说明如何复用。

除逐阶段的初态与解法验证外，还必须检查全部 N-1 个切换点（N=1 时无切换）：

1. 每节的不同参考解终局，均进入相同的下一节预设初态；不带入上一节胜利或物件状态，也不重复跳节。
2. 比较相邻阶段实际地形占格与地标，核对保留、移动、增删及其原因和连接关系；不因地形盒拆分/合并误报结构改变，也不要求旧范围全部保留。
3. 新出生点合法、有支撑、至少一个存活的有效 YOU、未获胜（多 YOU 按最新玩法合同，实际运行验证须等对应实现）；旧目标无意绕解、词牌全局作用和提示状态均已复核。
4. P1—PN 各自从固定初态回放，并完成一次整关连续流程；各阶段独立回放通过不能代替阶段切换验证。

当前设计工作流不等于游戏内阶段运行功能。阶段编辑改为各阶段独立地图文件；旧 `stagePlan` 仅兼容读取、切换和导出当前阶段独立地图，不再新增区域归属。正式运行目录现已接入 L01/L02 两关共六个独立地图，旧无阶段关卡退出游戏入口。目录支持有序阶段地图、胜利后自动切换与扩图展示、当前阶段重开；阶段进度只在当前运行会话内维护，未跨启动存档。现有 schemaVersion 9 关卡不会自动组成阶段序列，须在目录中显式配置并完成连续流程验证。

## 3. 逐关八工序与交付物

| 工序 | 要解决的问题 | 交付物 | 进入下一工序的条件 |
|---|---|---|---|
| 1 定位与目的 | 这关为什么存在？ | 序列位置、前置知识、核心认知或体验、可观察结果、预期误解 | 目标具体可检验，用户确认 |
| 2 空间结构与地图尺寸 | 地图如何承载目标和操作？ | P1—PN 目的与空间关系、各阶段尺寸、地形变化与连接口、主操作区、源词区、竖向净空 | 空间有依据，视角可读性有检查计划，用户确认 |
| 3 地图原型搭建 | 把空间方案变成可操作地图 | 逐阶段 JSON 原型、实际布局、世界词牌、地形与重布差异 | 文件和初态可检查；后续审查允许回修，用户确认或已有连续授权 |
| 4 教学方法与反馈 | 玩家怎样发现并理解因果？ | 基于原型的观察—行动—反馈—恢复表、提示方案和理解验收方法 | 教学反馈可行，不泄露解法，用户确认或已有连续授权 |
| 5 解题逻辑审查 | 谜题为什么成立？ | 基于原型的关键状态链、推动站位与退路、规则变化、死锁与绕解 | 必要操作可达，胜利逻辑成立，用户确认或已有连续授权 |
| 6 解法验证 | 能通关及检查绕解吗？ | 逐阶段参考解、关键事件、反例、切换与整关验证 | 解法有效，风险已处理，用户确认 |
| 7 盲测 | 玩家实际理解了吗？ | 非设计者首次试玩、提示、误解及迭代记录 | 真实观察支持目标，用户确认 |
| 8 定稿 | 哪个版本进入序列？ | 设计卡、关卡文件、解法和验证记录 | 版本一致，无阻断项，用户确认 |

确认遵循第 1 节的已有授权规则；本轮 L02 三阶段搭建已获连续推进授权，无需重复询问。没有真人试玩条件时，可完成工序 6 并交付“逻辑验证通过、教学待盲测”的候选，不能标为工序 7 或 8 通过。旧 L01/L02 卡片可保留历史编号，不因编号更新而要求返工；后续复核按本流程的内容门槛判断。

### 工序 1：把目标写成玩家能做到的事

使用句式：“已掌握【前置知识】的玩家，在【情境】下，能独立【关键决策/操作】，并解释【因果】。”

“学习 STOP”“难度中等”“有趣的推箱关”不够具体。可用的目标例句是：“玩家能根据 ROCK IS STOP 的存在判断岩块是否阻路，并通过拆句改变通行状态。”这只是目标写法示意，不代表已经批准重做 L02。

同时写明：在整个关卡序列中的作用、这一关不承担的新知识、玩家最可能的错误理解、目标体验时长与难度依据。时长和难度先作为假设，试玩后校准。不要用解法步数直接等同于难度。

### 工序 2：先定空间结构，再选尺寸

先写 P1—PN 各阶段目的、所需操作关系、地标、局部地形变化与连接方式，再计算各阶段尺寸。标出角色、障碍、目标与世界词牌的可读关系；完整实体坐标在工序 3 原型中落地。检查首次必需操作的前置知识。

#### 工序 2 尺寸预算：尺寸是有理由的预算，可以回修

先定能承载关卡目标的尺寸候选，再在工序 3 原型及工序 4—5 审查中检查教学方法和实际站位；不足时回到工序 2 修改。不要先锁死一个巨大空盒，再用物件填满。

必须分别列出：

1. 主操作区：各阶段所需动作空间、箱子/词牌目的格、玩家推动侧站位、绕行与撤退通道。
2. 世界源词区：全部句子的独立占格、底部支撑、必要隔墙及固定第 1 视角的阅读空间。源词区不是免费的屏外说明栏。
3. 竖向空间：底板、身体格、普通登攀/原地跳净空；涉及弹跳或上浮时，再计入完整运动与落点。
4. 完整边界：`X × Y × Z`，明确 X 是长度、Y 是高度、Z 是宽度；主操作区和源词区都必须纳入。

尺寸计算为 `各轴长度 = max - min + 1`，每轴允许 1–64 格。高度包含底板和所需净空，不能用“平面关所以 Y=1”替代计算。BOUNCY 的三格上升从接触格算起；FLY 需检查平台和乘客各自净空。

至少比较一个紧凑候选与一个宽松候选，注明多出的空间解决什么问题；选择承载教学与操作的最小充分空间。尺寸、箱子数、可动词数、同时有效规则数和推理依赖深度分开记录，不能认为地图越大难度越高。没有适用于全部关卡的固定推荐尺寸。

### 工序 3：搭建可回修的地图原型

依据工序 1—2，为 P1—PN 分别创建可导入的地图 JSON，记录文件、边界、实体坐标、词牌、出生点和相邻阶段的地形差异。原型应具备实际碰撞与规则，能够用于后续教学和逻辑审查；此时不声称解法、教学或整关流程已经通过。审查发现问题时回修原型及设计卡，并使受影响的下游结论失效。

### 工序 4：教学方法和提示分工

| 方法 | 适用目的 | 在本项目的检查点 |
|---|---|---|
| 聚焦与少量选择 | 让玩家发现当前关键对象 | 出生视野能辨认 YOU、当前目标、障碍和相关世界句子；避免无关词牌抢注意 |
| 安全试验 | 让玩家通过一次可恢复操作观察因果 | 保留 Z 撤销/R 重开；失控或卡死有可理解的反馈，恢复操作已教过 |
| 前后对照 | 分辨规则生效与失效 | 改写前后只突出目标变化；对照词牌、对象行为和实际可达性 |
| 环境引导 | 用站位、通道和朝向组织尝试 | 需要推动时可到达推动侧；普通登攀不能无意绕开本次关键体验 |
| 减少引导 | 检查独立理解 | 保留世界信息，撤去直接操作答案；记录帮助是否实际出现 |
| 条件变化 | 按本关目标检查适应能力 | 如需改变条件，保留已学规则；组合机制必须有前置 |

提示分为“提醒观察对象 → 指向因果关系 → 给出关键操作”。文本是补助，不能把每关变成按说明执行；用过操作答案的通关记录不能算独立检验通过。提示层级先写在设计卡中，不假设运行时已有按卡关程度自动升级的系统。

现有 `tutorial.regions` 只提供区域触发提示：首次进入、出生已在区内、换控后在区内均可能触发；不暂停操作，按队列限时显示。撤销和试玩内重开不重置触发记录，退出后重新进入试玩才重置。因此必须测试快速穿过、多条排队、换控和重新进入；不能把操作答案放在必经区域自动展示，也不能把区域触发当成玩家已经学会。

### 工序 5：基于原型审查关键逻辑

以关键状态而非长串移动命令描述解法：

`初态障碍 → 观察线索 → 关键操作 → 规则/空间变化 → 新的可达位置 → 两个不同实例同格获胜`

每一步写出：当前 YOU、目标对象、需要的推动方向、玩家站位、目的格、规则改变、支撑变化、后续退路。将状态链对应到工序 3 的实际坐标；若原型不支持预期解法，回修地图并重新审查。

推箱与规则改写至少审查：

- 角落、窄巷、贴边箱子、没有回身空间，以及“箱子能到、玩家推不到”的假解。
- 推链末端、推动后的返程、共用通道与操作顺序；项目没有拉箱。
- 文字也是可推实体；它可能变成垫脚石、挡路物或意外句子的一部分。不能只检查预期句尾词。
- 拆掉 STOP/PUSH 后的穿透、失去支撑后的下落、名词变形后的属性变化、NoControl 与多 YOU 回滚。
- 普通移动登攀、原地跳、弹跳、上浮、换控、变形是否能绕过关键体验；只检查本关实际提供的机制。
- 死锁分为“局面内可恢复”“需 Undo/重开”“触发不支持状态回滚”。教学段应尽早暴露恢复方法；有撤销不等于可以安排毫无反馈的长程死锁。

本项目的箱子默认下落，性质取决于世界句子；不能直接套用传统二维推箱子“墙角永远死锁”等结论。所有死锁判断需说明当前规则、可用变形及恢复方式。

### 工序 6：解法验证证据

在工序 3 原型上保留教学与解题需要的地形、物件、词牌与提示，按工序 4—5 的审查结果回修；使用编辑器真实 Parser、初态校验、隔离试玩、参考解录制与回放。

| 验证层 | 要证明的事 | 不能据此声称 |
|---|---|---|
| 数据与初态 | 版本正确、ID/占格/边界/支撑合法、恰好一个 YOU、初态稳定且未获胜 | 关卡可解或好玩 |
| 参考解 | 当前灰盒从同一初态可通关，事件与策略声明相符 | 唯一解、最短解、所有路径都符合教学 |
| 反例与绕解 | 已检查特定绕路、拆句、登攀和死锁；有搜索时记录覆盖 | 有限尝试或限额搜索等于穷尽证明 |
| 固定视角可读性 | 实际 Game View 能看清世界词牌、动作反馈和遮挡关系 | 编辑器能看清就等于玩家能看清 |
| 真人教学 | 非设计者展示本关预期的因果理解与操作 | 作者自己通关或自动回放等于教学有效 |

参考解录制成功后逐条从同一初态回放；不同策略要有不同的关键决策/机制，而非绕路长短。当前事件要求只验证路径类别，不改变游戏获胜规则。布局、词牌、初态或规则合同改变后重验全部受影响参考解，并记录文件 SHA-256、验证工具/版本、日期、结果与局限。

反例报告必须区分：找到反例、在已尝试范围内未找到、在明确范围内穷尽、未执行。搜索限额用完时写“未证实”。旧 Pack 的 Python 检查针对包内布局和有限模型，不能代替当前 `Assets` 关卡的 Unity 验证；该脚本还会回写包内数据，不应为文档核查随意运行。

### 工序 7—8：盲测、回退与定稿

至少安排一次非设计者的首次试玩观察；这只是最小反馈门槛，不是统计证明。记录试玩者的相关游戏经验和已学前置，不收集无关个人信息。设计者尽量不口头引导；若提供帮助，记下时间、内容和原因。没有合适玩家时保留“待盲测”。

记录首次关注对象、首次有意义行动、错误假设、首次卡点、Undo/重开、提示、通关时间，并在结束后请玩家解释关键因果。检验是否通过要同时看行为和解释，避免只靠自述。

| 观察结果 | 优先回到的工序 |
|---|---|
| 不知道目标或不知道看哪里 | 1 定位 / 4 教学方法 |
| 会照做但不会解释因果 | 1 目的 / 4 教学方法 |
| 必需操作缺少前置知识 | 1 前置知识 / 4 教学方法 |
| 想对了，但站位不足或搬运冗长 | 2 空间尺寸 / 3 地图原型 / 5 解题逻辑 |
| 绕过本关目的仍轻松通关 | 1 定位 / 5 解题逻辑 |
| 词牌被遮挡或提示排队泄露答案 | 2 空间 / 3 地图原型 / 4 反馈 |
| 回放失效或出现不支持状态 | 3 地图原型 / 5 解题逻辑 |

修改时写清一个主要假设、对应改动及复测结果。重复试玩者已知道答案，其反馈可用于操作与可读性复核；不能冒充首次教学效果。定稿前重新核对前后关的认知衔接，归档当前版本证据。

## 4. 本项目必须保留的玩法边界

- 全部显式规则由世界里的独立 Text 组成，全部 `anchored=false`；不使用 `fixedRules` 或按关卡 ID 注入属性。隔离源词也需要真实支撑、空间和可读性。
- 普通方向统一移动与推动可推物件/词牌，推动失败则停止；禁止翻越，不使用 Shift 推动；原地跳无水平分量。玩家与试玩固定第 1 视角，作者编辑视角可旋转。不能按旧文档的 Q/E 玩家转镜头来设计读图。
- 获胜允许实例自身同时 YOU/WIN，或两个不同 YOU/WIN 实例合法同格。没有 PUSH/STOP/YOU 的物件可能可穿过，WIN 本身不取消实体性。
- 初态单 YOU，拆句失控可撤销；多 YOU 和当前不支持的受控 HOVER/FLY 组合不能作为必需解法。WALL 专属翻越规则尚待确认，不能假定存在不可翻越例外。
- 作者初态一格一个可见方块，不改变运行时合法同格接触语义；所有初始物件、文字、地形与透明隔墙都要检查占格。
- 2026-09-25 已确认：L01 参考解是推岩块，L02 是拆 ROCK IS STOP，L03 出生即 CLOUD IS YOU。旧包的前三关命题不能直接覆盖这些决定。新工作流也不等于已经确认新的关卡命题。

## 5. 现有关卡如何迁移

本次只建立流程，不重做 L01—L12，不追认任何一关已通过新工序或多关卡联合审核。

后续开始某关时，在 `docs/level-design/` 建立该关设计卡，状态记为“旧关待复核”；读取当前实际关卡和最新用户决定，先填写工序 1，再依序补齐。不能将旧布局反向包装成已审核设计。序列重排须同时检查前置知识与跨关链。旧 L01/L02 设计卡保留历史编号，不强制按新编号返工。

当前 [实施状态](IMPLEMENTATION_STATUS.md) 记录了 L01 参考解、出生提示和无互动通关等内容验收问题；这是后续复核输入，不能沿用较早“十二关全部通过”的历史记录。本流程没有重新运行这些测试，也没有确认问题已经修复。

设计卡放在 Markdown 中，引用现有 JSON 路径和哈希；不新增运行时必填字段，不提升 schemaVersion。未知元数据能够保留，不意味着编辑器理解或执行了这些流程状态。

## 6. 多关卡联合审核：Teach–Test–Twist

逐关完成并获得解法与盲测证据后，按关卡序列联合检查同一核心认知：Teach 让玩家在有反馈的情境中亲手建立因果；Test 在减少引导后检查能否独立应用；Twist 在规则一致、条件变化时检查能否迁移。三个环节可以分布在不同关卡及各关的不同游玩阶段，不要求每关各有一套，也不决定 P1—PN 的数量。

联合审核记录每个环节所在关卡与阶段、前置知识、玩家关键行动、所见反馈及实际验收证据。Test 不能只靠碰巧通关，Twist 不能只靠扩大地图、加长搬运或增加箱子；若变式引入未教知识，补齐前置教学和验证。发现缺口时回到相关关卡的对应工序修订，再重验受影响解法与盲测。不因逐关定稿就自动认定整组关卡的教学链通过。
